# Interactive state BFF v1 — draft, inactive foundation

This PR implements the BFF operation lifecycle and validates the actual Converter Python snapshot/receipt schema with a synthetic fixture. **It does not complete the interactive-preview design or connect a live Converter worker.** `runtime.ts` deliberately supplies an unavailable worker and `converterTransportAvailable=false`; setting `INTERACTIVE_STATE_ENABLED=true` cannot bypass that gate. No schema is frozen and no rollout, deployment or paid evaluation was performed.

Base: BFF develop `37adaa616b21ac49933974f73b56fbc5c575b0c2`. Design: `Standin-server/docs/NEXT_SPRINT/INTERACTIVE_POSE_PREVIEW_ASYNC_FBX_DESIGN_2026-11-04.md`. Machine-readable draft: `docs/contracts/bff-http-contract-v1.json`. Converter draft: `Standin-server/artifacts/interactive-preview-20261104/converter-contract-v1.json` (branch `codex/interactive-pose-converter-v1`, base `592ab0f059089e64a5c88a3ad607539124e8e6c6`). The fixture records SHA256 of the exact Python sources observed before commit; those are draft sources, not a released worker version.

## Implemented boundary

Existing installation authentication covers the additive `/v1/analysis/jobs/:jobId/people/:personIndex/interactive-state` routes. First persist the candidate confirmation and body/hand/scope selection using existing APIs. POST prepare accepts only a candidate ID, increasing revision, expected previous revision/hash and a mutation ID. It never accepts client bones, meshes or matrices as pose authority. Each person has its own durable head, so one person's change does not supersede another's file.

Prepare returns 202 without solve/export/PNG work. GET polls the operation (suggested 1 second); `eventSequence` orders response updates. SSE is not implemented. Duplicate mutation IDs replay only identical requests for the same still-current server selection. A different payload returns 409. Revisions may skip numbers but must increase; `expectedRevision` is mandatory and `expectedStateHash` is compared when non-null. A new client session can GET the base path with `?candidateId=...` to recover `currentRevision`, `currentStateHash` and the still-applicable operation. Expired or superseded selection metadata returns a null operation while preserving the monotonic revision.

`selectionHash` is an immutable canonical fingerprint of server-owned installation/job/person/candidate, original/output BVH and refine result metadata, body/rig/shape/source, hand library/revision, scope, camera and existing runtime identities. Paths, clocks, names and observation orbit are excluded. `stateHash` starts null; solve assigns the SHA256 of Converter's exact ASCII `typed-f64be-json-v1` snapshot bytes once. BFF does not hash a decoded JavaScript re-stringification of the geometry. Snapshot identity/model/runtime proof is retained separately and checked against the final receipt.

The resolver rereads owned job and candidate membership, explicit current confirmation, release/manual review policy, body/shape, hands, scope, camera, base-source availability/quarantine and lineage, refined bytes and runtime. It runs at prepare, polling, worker publication and byte delivery, including a final recheck after worker/file reads. A hash, source, hand or selection change prevents delivery of an old ready file. Semantic/preview-only candidates gain no permissions from a 3D view.

PostgreSQL rows and parent-job locks serialize per-person compare-and-swap. Independent preview/export/poster leases bound each stage to one BFF dispatcher across replicas. Active work is renewed every second; cancelled/deleted/superseded/expired rows fail renewal and abort the local signal. A lost process's lease can be reclaimed after 30 seconds. The actual worker transport must honor the operation ID as its idempotency key and abort/cancel in the Converter process; that remote connection is **pending**, not tested. No already-running Blender process is claimed to be preempted by the BFF-only fixture.

The service validates `solved-pose-state-v1` including bounded bones, topology, split normals, skin weights, exact canonical bytes and source/selection identity. It validates `interactive-fbx-receipt-v1`, original tolerances and same state/revision/identity/model/runtime proof. File delivery checks size, FBX signature and actual byte SHA256. `previewState=authoritative` alone never enables a file. A failed export leaves the authoritative preview available. No fake validating progress is emitted; the current adapter reports building until a verified receipt is returned.

## Static history and auxiliary capture

After a verified export, a separate poster slot renders the exact persisted FBX with the existing renderer, using the existing front reference view. This is a static representative image, not a claim to reproduce the rough's search projection. `interactive_history_frames` archives metadata bound to server revision, stateHash, image SHA and renderer. The head/revision check prevents an old render from overwriting a newer frame. The operation/file lifetime is one hour; a history frame follows the owned job's existing retention/deletion policy, and its delivery still revalidates the current server selection and source. No image is generated during a history list request.

The existing `thumbnailUrl` and natural-language result posters are retained. An additive `representativeFrame` can reference the archived server frame when enabled; a missing/stale/failed frame uses the existing static image/placeholder. Image lookup failure cannot fail the list or export. New tables join existing job/installation deletion and consent-withdrawal registries. Image objects use the existing private installation/job prefix and bucket lifecycle/deletion policy; no new public URL or filename appears in telemetry or replay.

POST `/{operationId}/client-frame` accepts at most 1 MiB PNG bytes (JSON/base64 envelope ≤1.5 MB), exact image hash, current revision/stateHash, bounded renderer ID and a claimed camera hash. It is **auxiliary UI data**; the client must capture only the doll canvas. The server does not attest what the pixels contain or treat the claimed camera hash as evidence. One auxiliary image is stored per operation (same-hash retries are idempotent). It never populates the authoritative history frame or authorizes export. Capture failure/app exit does not gate list/save.

## Preserved paths and metrics

Legacy `framed?format=ready` keeps `previewFormat:none` and `verified-fbx-v1`. PNG remains a separate exact-FBX render. Existing body/hand review, individual export, scene and disabled-auto-save paths are preserved. Top-5 `/preview-model` stays cache-only; a cache miss cannot invoke conversion or PNG, and a candidate/source change during asset retrieval is rechecked before delivery. Static GLB validation is unchanged. A complete Top-5 model/byte/SHA/camera coverage manifest is still pending; the new capability must not be advertised from rotation alone.

New preparation metrics use `artifact_prepare_started/ready/failed/cancelled`, with preview/export/poster stage and elapsed time. They omit original names, paths, packets, bytes and tokens. `artifact_download_delivered` means an explicit HTTP file delivery only. Preparation does not call `recordExport(completed)`, and neither event claims native disk persistence. Existing quality/replay consent and collection settings are unchanged.

## Evidence and remaining activation requirements

- `npm run typecheck` and `npm test` cover the new Hono routes and actual SQL store/queue with PGlite, plus existing regression suites. PGlite serializes transactions and lacks advisory locks; that one call is bypassed in its adapter. PostgreSQL replica/advisory-lock contention is not thereby verified.
- `fixtures/converter-packet.json` is a synthetic 3-vertex state generated by actual Converter Python serialization, with source hashes. Tests consume its canonical bytes, model and receipt through the real BFF service. The synthetic receipt is **not** a successful Blender export or real asset safety proof.
- Required before activation: freeze a common versioned HTTP solve/model/export/file/cancel contract; implement the `InteractiveWorker` port against those actual routes; verify worker idempotency/restart and real cancellation; bind new solver/runtime, hand library, shape recipe and refine algorithm/run identity from the agreed runtime contract; supply exact authoritative camera matrices/torso/coordinate mapping; complete full Top-5 asset coverage; pass real FBX split-normal/pose/skin/topology correspondence without relaxing checks; run real PostgreSQL multi-replica and private storage/retention tests; run actual app/native save/scene/CSP and cold/warm performance comparisons; user UI acceptance and final activation review.
- Converter currently retains its initial/intermediate FBX dependency. This PR does not claim pre-initial-FBX solve or p50/p95 performance improvement.
